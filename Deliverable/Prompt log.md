# AI Prompt Log
## Cybersecurity Assessment Project — Team Zero Trace | CONFIDENTIAL

**Prepared:** June 2026 | **4 Members** | **40 Prompt Interactions**

---

> **Purpose of this log**
> This document records how AI tools were used by the four members of Team Zero Trace during the cybersecurity assessment engagement. Each entry captures the objective the member had in mind, the prompt they actually typed, and what came back. The intent is to make clear that every AI interaction was human-directed and human-validated — AI was used as a drafting and thinking aid, not as a replacement for professional judgement. All findings, conclusions, and recommendations in the final deliverables represent the team's own assessments.

## Indrajit Singh
### Team Lead & Lead Security Analyst


---

**Contribution Summary**

Indrajit led the engagement end-to-end — from initial scoping through to final deliverable sign-off. On the technical side, he drove both the network forensics workstream and the web application security testing, handling everything from PCAP triage and C2 analysis to injection testing and business logic review. Beyond the hands-on assessment work, he owned the threat model, the attack-path narrative, and the overall risk position presented to the client. Executive reporting, remediation prioritisation, and the final review of all outgoing documents sat with him. His prompts reflect the dual nature of the role — part analyst working through live evidence, part lead trying to make sure the whole thing hangs together as a coherent deliverable.

---

| # | Objective | Prompt | Outcome |
|---|---|---|---|
| 01 | Get a structured starting point before diving into the PCAP | *okay so i've got the capture file and i'm about to start going through it. before i do that help me put together a checklist of things i should actually be looking for — C2 indicators, lateral movement, credential theft stuff. keep it practical i don't need textbook definitions* | Generated a triage checklist covering beaconing intervals, DNS anomalies, SMB named pipe patterns, and LSARPC/SAMR activity — used as the opening framework for the network forensics workstream. |
| 02 | Figure out whether unusual DNS traffic is C2 or something benign | *i'm seeing a bunch of DNS queries going out to some weird TLDs — .su, .sbs, .cc and a couple others — from one internal machine. the timing is regular but not crazy in volume. is this C2 beaconing or could it be something legit? what would i need to see to confirm it either way* | Confirmed the pattern as consistent with C2 domain rotation. Provided secondary indicators to validate including JA3 fingerprints and TLS certificate anomalies — used to build the initial C2 finding. |
| 03 | Write up the C2 communication chain for a technical audience who hasn't seen the PCAP | *need to write this up for the report. workstation is 10.1.21.58, it's talking to a domain that resolves to an external IP, traffic is HTTP to a specific endpoint. how do i frame this so a technical reader who hasn't looked at the capture can follow it* | Produced a clear technical narrative covering the communication chain, IOCs, and endpoint significance — used as the base for the Phase 1 attack path section. |
| 04 | Explain what the LSARPC and SAMR activity actually means to a non-technical stakeholder | *i've got a lot of LSARPC and SAMR frames from the compromised machine going to an internal server. i know it's account enumeration but i need to be able to explain to someone non-technical exactly what information the attacker gets from this. help me frame that* | Drafted a plain-language explanation of what LSARPC and SAMR expose — user accounts, group memberships, password policies — and how that feeds into the next exploitation phase. Used in Phase 3 of the attack narrative. |
| 05 | Scope the web app test before touching a live financial services environment | *about to start the web app assessment on a live B2C financial portal — there's real customer data in there. help me think through the testing sequence given the risk profile, and flag anything i should specifically avoid doing on a live system* | Produced a risk-prioritised testing sequence starting with authentication, then injection points, then business logic — with explicit safety notes around live transaction endpoints. Used as the Workstream B engagement plan. |
| 06 | Work out the right severity for the SQL injection finding without actually exploiting it | *found what looks like a SQL injection on the login form — error messages are leaking stack traces, i'm getting boolean-based responses. i haven't pushed it on a live system. how do i document this as confirmed without pulling data, and what exploitation path do i describe* | Provided a documentation framework for confirmed-but-not-exploited SQLi, including the evidence threshold for Critical classification and a written exploitation narrative — filed as the lead finding in the web app workstream. |
| 07 | Validate the IOC list before sending it to the client | *before i hand the IOC list to the client i want to sanity check it. i've got the domain, the IP, and the C2 endpoint path. anything else i should derive from what i've described? and what format makes sense for the client — STIX, CSV, just a table* | Suggested additional derived IOCs including the full URL pattern and TLS fingerprint, and recommended a simple structured table for client delivery given the audience. Final IOC list formatted accordingly. |
| 08 | Write a threat model that's actually grounded in the engagement findings rather than generic | *i need to build the threat model for this environment based on everything we found. want it structured as assets, threat actors, entry points, key threats, business impact. help me populate from the actual findings rather than writing something boilerplate* | Produced a fully populated threat model pulling directly from both workstreams — used as the source document for the threat model deliverable and the visual threat model diagram. |
| 09 | Prepare talking points for the client debrief with the CTO | *we've got a call tomorrow, their CTO is on it and they want to know what the attacker was actually doing and whether they got to what they were after. give me five or six talking points i can use to structure the conversation — not scripted, just things i can work off* | Generated six plain-language talking points covering attacker timeline, confirmed vs inferred activity, and immediate containment advice — used to structure the debrief call. |
| 10 | Review the full attack path document before it goes out | *can you read through this attack path section and tell me if the logic holds — does the evidence actually support the conclusions or am i making any leaps a client could push back on. i want every claim tied to something observable* | Identified two claims needing stronger evidential grounding and one section where language overstated certainty — qualifier language suggested and incorporated before final submission. |

## Chaitanya
### Evidence & Repository Coordinator

---

*Contribution Summary*

Chaitanya was responsible for keeping the engagement's evidence base clean, traceable, and submission-ready throughout. That meant managing screenshot verification, maintaining the repository structure across both workstreams, coordinating version control so nothing got overwritten or lost, and making sure every artifact going into the final deliverable was properly logged and accounted for. It's the kind of work that doesn't show up in the findings but absolutely shows up if it isn't done — inconsistent screenshots, mislabelled files, or a version confusion on the final night will sink a report. His prompts reflect someone who was thinking carefully about process, not just ticking boxes.

---

| # | Objective | Prompt | Outcome |
|---|---|---|---|
| 01 | Set up a repository structure that works for a multi-workstream engagement before anyone starts dumping files | we're about to start a two-workstream security assessment and i need to set up the repo before people start dropping files everywhere. what's a sensible folder structure for something like this — network forensics on one side, web app on the other, plus shared docs and evidence. want it organised from day one not cleaned up at the end | Produced a clean two-workstream folder hierarchy with dedicated directories for raw evidence, processed screenshots, findings drafts, and shared deliverables — adopted as the master repository structure for the engagement. |
| 02 | Work out a screenshot naming convention that makes it obvious what each file is without opening it | i need a naming convention for screenshots that makes sense across both workstreams. someone should be able to look at the filename and know roughly what finding it relates to, who captured it, and when — without having to open it. what's a practical format for that | Proposed a naming convention using workstream prefix, finding ID, a short descriptor, analyst initials, and date — adopted as the team standard and applied retrospectively to existing screenshots. |
| 03 | Understand what actually needs to be captured as evidence to make a finding defensible | one of the analysts flagged a finding but the evidence is a bit thin — there's a screenshot of the response but no request, no context. what does a properly evidenced finding actually need to include to hold up if a client pushes back on it | Outlined the minimum evidence requirements for a defensible finding — request, response, context, analyst notes, and timestamp — used as the evidence checklist distributed to the team. |
| 04 | Do a version control check before the final report draft goes to the lead for review | i need to do a version check before the draft goes to indrajit. there have been a few people editing things at different times and i want to make sure we're not about to hand over something with conflicting content from two different versions of the same section. how do i approach this systematically | Provided a structured version reconciliation approach covering file timestamps, change logs, and section-by-section comparison — used to resolve two identified conflicts in the Workstream A findings before handoff. |
| 05 | Figure out how to handle an analyst's screenshots that don't clearly show the tool output | one analyst sent me screenshots but some of them are cropped in a way that cuts off important parts of the output — like the status code or the full request. i need to raise this without making it a big deal but the evidence genuinely isn't usable as-is. how do i handle that | Produced a brief, professional evidence re-capture request template — used to get clean replacements from the analyst within the same working day without any friction. |
| 06 | Work out what goes into the evidence submission package and in what format | building the evidence submission package for the final deliverable. what should actually be in it — raw screenshots, processed versions, pcap excerpts, tool output logs? and is there a standard way to package this or is it just a zip with a readme | Outlined a structured evidence package format with an index sheet, organised subdirectories by finding ID, and a README covering what each artifact demonstrates — adopted as the submission package structure. |
| 07 | Do a pre-submission readiness check before anything goes to the client | we're two days out from submission and i want to do a readiness check on the evidence side. what should i be looking at — completeness, naming, cross-references to the report, anything else? i want a checklist i can actually work through | Produced a pre-submission evidence checklist covering file completeness, naming convention compliance, finding cross-references, and artifact log accuracy — completed and signed off 48 hours before submission. |
| 08 | Verify that every finding in the report has a corresponding evidence artifact | i'm doing a cross-reference check between the findings in the report and the evidence in the repo. some findings reference screenshots by filename but i want to make sure every single one actually exists and is in the right place. what's the quickest way to do this systematically | Suggested a cross-reference methodology using the findings table as the source of truth and checking each referenced artifact against the repository index — identified two missing screenshots which were re-captured and added. |
| 09 | Write an artifact tracking log entry format that anyone on the team can fill in consistently | i need the team to log artifacts as they go rather than at the end. what's a simple log entry format that captures everything useful — what it is, where it is, who made it, what finding it supports — without being so long that people don't bother filling it in | Produced a concise artifact log entry template with seven fields — used as the team's artifact tracking standard for the remainder of the engagement. |
| 10 | Final check on the repository before closing it out after submission | engagement is done and i'm about to archive the repo. what's a sensible final check before i close it out — is there anything i should make sure is in there, anything i should clean up, any kind of sign-off record i should create | Outlined a repository closeout checklist including a final file count, confirmation of evidence completeness, removal of any working files not intended for record, and creation of a closeout log — completed and archived. |

## Pushpendra Sahu
### Reporting & Compliance Support

---

**Contribution Summary**

Pushpendra handled the reporting infrastructure — the stuff that makes a technical document actually usable as a professional deliverable. That included enforcing formatting consistency across sections written by different analysts, running compliance checks to make sure the report structure met the engagement's stated methodology, verifying that risk ratings were applied consistently against a defined framework, and supporting the final executive report for the client. His work in the last 48 hours before submission was particularly load-bearing — the final submission review, compliance cross-check, and quality gate before anything went out. The prompts reflect someone balancing precision with pragmatism, trying to get things right without holding up the team.

---

| # | Objective | Prompt | Outcome |
|---|---|---|---|

| 02 | Build a risk-rating consistency check before the final ratings go in | *we need to make sure the risk ratings across all findings are being applied against the same criteria — i don't want the client to look at two similar findings with different ratings and ask why. help me put together a quick consistency check i can run before the ratings are finalised* | Produced a risk-rating consistency matrix mapping each finding against the agreed criteria — identified two findings where ratings were inconsistent with the framework and flagged for lead review. |
| 03 | Check whether the report structure meets the compliance requirements for the engagement | *i need to check whether the report structure actually meets the compliance requirements we committed to in scope. we said we'd follow a specific methodology and i want to make sure all the required sections are present and in the right order before this goes anywhere near the client* | Provided a compliance checklist cross-referencing the agreed methodology against the draft structure — identified one missing section (risk acceptance statement) that was added before the final draft. |
| 04 | Write a formatting guide for the executive report section | *the executive report section needs to look different from the technical body — simpler, less dense, easier to read at a glance. help me put together a short formatting guide for this section so whoever writes it is working to the same standard* | Produced a one-page executive report formatting guide covering font sizing, use of summary boxes, traffic-light risk indicators, and recommended section length — used as the formatting brief for the executive report. |

| 09 | Write the submission cover note | *i need to write a short cover note to go with the submission package — something professional that confirms what's being submitted, who prepared it, and any important caveats the client should be aware of. keep it brief* | Produced a submission cover note template covering deliverable list, preparation team, engagement scope, and key caveats — reviewed by the team lead and used as the submission cover letter. |
| 10 | Create a post-submission QA record for the engagement file | *now that we've submitted i want to create a record of the QA work done on this engagement — what was checked, what was found, how it was resolved, who signed off. this is partly for the engagement record and partly so we can learn from it. what should this document include* | Produced a post-submission QA record template covering review scope, issues identified, resolution actions, sign-off chain, and lessons learned — completed and added to the engagement archive. |
